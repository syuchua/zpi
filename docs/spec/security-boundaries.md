# Security boundaries and execution policy

Status: design and evidence map for the experimental v0.1.0 implementation. This document describes existing behavior; it does not introduce an approval prompt, project sandbox, privilege boundary, or new default. Zpi runs with the OS permissions of its launching account. Tool selection controls which model-callable tools are registered; it is not a process sandbox and does not by itself prevent explicitly selected extensions, plugins, or MCP commands from loading.

## Threat model

Treat model output, session imports, project files, tool results, extension code, plugin libraries, MCP executables, endpoint configuration, and downloaded web content as potentially hostile. The principal risks are unauthorized filesystem/process/network effects, credential disclosure through inherited environment or output, malicious code execution during explicit component loading, partial/unknown effects after interruption, and unsafe assumptions about isolation between child processes or native code.

The trusted computing base includes the Zpi binary and its dependencies, the user's OS account and filesystem permissions, selected provider endpoint/configuration, any executable path deliberately supplied by the user, and the terminal/parent process. The following are **not** security boundaries: `--cwd`, tool allowlists, `--no-tools`, a Node child process, MCP stdio, subagent conversation separation, cooperative cancellation, or a session file. They constrain workflow or protocol behavior but do not reduce OS privileges. In-process native plugins can corrupt or terminate the host process; child processes inherit the launching account's accessible resources and ambient environment unless the parent environment is externally restricted.

## Execution policy matrix

| Surface | How it is enabled / default | Execution identity and effects | Fail-closed behavior and evidence | Boundary / expected trust |
| --- | --- | --- | --- | --- |
| Interactive native tools | Core file/shell tools are selected by CLI/settings; `--tools` filters model declarations and dispatch, `--exclude-tools` is final, and `--no-tools` disables model tools unless explicitly re-enabled | Same OS user; enabled `bash` can run arbitrary commands, and file tools can access account-readable/writable paths, not only `--cwd` | Offline fake-provider fixture asks for a disabled `write`; result is `Unknown tool` and `forbidden.txt` is absent (`scripts/test-cli.py`, `disabled-effect`). Search and URL tools also have argument/SSRF checks | Selection is not approval or filesystem confinement. Use a restricted OS account/container for hostile input |
| `-p` / print and JSON output | Explicit CLI mode or prompt arguments | Same harness and tool permissions as interactive mode; non-interactive invocation is not implicitly read-only | Same tool filtering/dispatch path and offline no-effect fixture. Invalid credentials, models/config, headers, prompt files and routing are rejected before session/plugin effects in named fixtures | `--print` changes UI/output mode, not authority. Explicitly choose `--no-tools` or a restrictive tool set |
| RPC (`--mode rpc`) | Explicit CLI mode; accepts a bounded JSONL request protocol | Same process and tool permissions as the harness options; requests can invoke enabled tools through provider turns | `scripts/test-cli.py::check_rpc` covers malformed/oversized frames, unsupported command, busy rejection, cancellation, provider error, recovery, EOF and no session effect for idle state. It runs `--no-tools`; it is not a privileged RPC server | Treat the RPC peer as an authorized controller. No authentication/remote listener is provided by this stdio transport; do not expose its pipes to untrusted clients |
| MCP stdio | Each executable and argv is explicitly supplied with repeatable `--mcp-stdio`; tool names are then subject to normal selection | Child process runs as same account and inherits ambient environment; MCP tools can cause arbitrary effects within its permissions | CLI fixtures cover disabled/excluded MCP calls without dispatch, output bounds, protocol errors and tool results (`scripts/test-cli.py`, `mcp-disabled`, `mcp-excluded`, `mcp-opt-out`) | Explicit selection authorizes code startup. Tool filtering does not necessarily prevent the server process from being initialized. Review executable, argv and environment |
| Background tasks | `bg_run` must be enabled and invoked by model/user workflow | Shell command runs in a process group as same account; may access filesystem/network and inherited environment | Bounded lifecycle/log tests cover process-group termination and `bg_kill`; see `src/bg_tasks.zig` tests and TUI CLI fixtures | Process group cleanup is not a sandbox; grandchildren or kernel-level effects may outlive cooperative cleanup |
| Native subagents | Experimental `subagent` tool is opt-in via tool selection | Child agent gets a fresh in-memory conversation but eligible parent-enabled tools, same working directory/account, and shared filesystem | CLI fixtures cover inherited read-only selection, write effects, deadlines, parent cancellation and result bounds (`check_subagent`) | Conversation isolation is not privilege isolation. Assign distinct files for concurrent children; use OS controls for untrusted tasks |
| TypeScript extensions | Explicit `--pi-sdk`/host and `-e PATH`; no project/global autodiscovery | Trusted JavaScript runs in a Node child with the launching user's permissions and ambient environment; can access resources independently of tool allowlists | Host validates protocol, SDK version, schema and deadlines; CLI fixture verifies a denied write leaves no file and malformed/invalid inputs fail; see `docs/spec/typescript-extension-host.md` | Child-process boundary provides lifecycle control, not sandboxing. An extension may directly use Node APIs or spawn children |
| Native C/Zig plugins | Explicit repeatable `--native-plugin PATH`; plugin is loaded at startup, including when model tools are disabled | Dynamic library runs in-process as the host; library constructors execute before descriptor/tool filtering; full memory/process authority of host | Descriptor/ABI checks reject malformed tables; tests cover disabled tool dispatch and invalid descriptors; see `docs/spec/native-plugin-runtime.md` | Highest-risk extension surface: no memory safety, crash containment, or sandbox claim. Do not load untrusted libraries |
| Skills and prompt templates | User resources may be discovered; project resources require explicit trust flags; explicit paths are user-directed | Text is inserted into model context; no code is executed by the loader, but instructions can induce later tool actions | Parser/path/bounds and opt-out fixtures; project discovery is gated by `--trust-project-skills` / `--trust-project-prompts` | Treat content as untrusted instructions. A trust flag authorizes prompt influence, not code execution or OS confinement |
| Provider/config/session data | Explicit models/config/session options and environment | Provider sees submitted context and credentials in configured requests; session stores conversation/tool results locally | Config and secret-bearing errors are bounded/redacted in covered fixtures; session creation uses restrictive file modes and locks | Verify remote endpoint and keep credentials/session backups private. `--no-session` avoids persistent conversation history, not provider transmission |

## Fail-closed behavior and current tests

The current release has several fail-closed paths, but they are local validation properties, not a comprehensive reference monitor. Regression suites completed on 2026-11-23: the fresh-cache macOS debug build ran 203/203 tests and the CLI, TS host, and native plugin fixtures passed (`b0ca1309f`); the v0.1.0 ReleaseSafe archive CLI fixture passed; the headless build ran 180 tests with three documented SDK skips and passed both RPC fixtures (`b6768b9f3`). These runs cover the specific denial cases below, not a security audit.

- Tool allowlisting is applied to both declarations and dispatch. The disabled-write fake-provider test verifies that a model-proposed write does not create a file.
- MCP tool filtering/exclusions are checked against the server call log. This prevents the filtered call, but the explicitly requested MCP process remains trusted startup code.
- Extension gate denial is tested before the requested write effect; the fixture checks that the target file does not exist.
- Invalid credential/config/model routing/prompt input checks in `scripts/test-cli.py` assert failure before the named session path or explicitly missing plugin path has an effect.
- RPC validates frame size, UTF-8/JSON structure, depth/token bounds, supported command and prompt arguments. Errors are serialized on stdout; stderr is not a separate authenticated control channel.
- `web_fetch` blocks private/loopback/link-local and other reserved addresses by default, validates redirects and connected peers, and requires an explicit loopback opt-in for local fixtures.
- Session resume rejects unsafe file types/locks/corruption; an interrupted tool may have an unknown outcome and is not automatically replayed.

Run the available regression suite on the current host with Zig 0.17.0:

```sh
zig build test install
python3 scripts/test-cli.py
python3 scripts/test-ts-host.py "$ZPI_PI_SDK"  # when the supported SDK is installed
```

The test suite uses local fake providers/servers and temporary directories; it does not prove the absence of all side effects, provide a security audit, or test malicious native code. Linux TypeScript SDK execution and OS-level sandboxing are not established by these checks.

## Policy decisions intentionally deferred

No new default permissions or approval UX are introduced here. Before adding project trust prompts, per-command approvals, remote RPC authentication, environment scrubbing, or process sandboxing, define the threat actor, compatibility impact, headless behavior, persisted policy, bypass semantics, and rejection behavior. In particular, tool selection must not be presented as consent to run explicitly loaded code, and process cleanup must not be presented as containment.
