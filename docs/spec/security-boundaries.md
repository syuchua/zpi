# Security boundaries and execution policy

Status: design and evidence map for the experimental implementation. This document describes existing behavior and boundaries. The opt-in policy contract is in [security-capabilities.md](security-capabilities.md); it does not change the default. Zpi runs with the OS permissions of its launching account. Tool selection controls which model-callable tools are registered; it is not a process sandbox and does not by itself prevent explicitly selected extensions, plugins, or MCP commands from loading.

When `--security=secure` is explicitly selected, the host adds pre-effect capability and target-rule checks to built-in tool dispatch, user shell, clipboard copy, RPC `prompt`, MCP startup, TypeScript host startup, native-plugin loading, and child-Agent tool dispatch; enables OS confinement (`--sandbox workspace-write`, `--sandbox-network off`) and strict child environment allowlisting (`--env-isolation strict`) by default; and enforces canonical-path workspace containment on built-in file tools. `--audit-log` is required in secure mode and for request-scoped grants. The default compatibility mode remains unchanged (`--sandbox off`, `--env-isolation inherit`, `--subagent-isolation shared`); a configured audit log records the same host-observed checks with policy source `compatibility`.

## OS confinement and credential isolation

The shared confinement boundary (`src/sandbox.zig`) covers process-capable execution across `bash`, interactive user shell, `bg_run`, `rg`/`fd`, MCP stdio servers, the TypeScript extension host, and subagent child processes:

- **macOS**: Seatbelt (`/usr/bin/sandbox-exec`) with a default-deny SBPL profile allowing read-only system runtime trees and the canonical workspace, writes only inside the canonical workspace (or none in `read-only` mode), explicit deny rules for host credential directories under `$HOME` (`.ssh`, `.aws`, `.gnupg`, `.zpi`, `.pi`, `.kube`, `.docker`, `.netrc`, `.npmrc`, `.pypirc`, `.git-credentials`), and `(deny network*)` when `--sandbox-network off`.
- **Linux**: Landlock LSM (ABI v1–v5) filesystem and TCP rules plus a classic-BPF seccomp filter denying `AF_INET`/`AF_INET6`/`AF_NETLINK`/`AF_PACKET` sockets via a self-exec trampoline (`--zpi-internal-sandbox-exec`), with automatic fallback to `bwrap` (`--unshare-net`, read-only system binds, private `/tmp` tmpfs, `--die-with-parent`) when Landlock is unavailable. Fails closed (`SandboxUnavailable`) if no backend is available.
- **Built-in file tools**: canonical-path resolution (`resolveToolPath`) resolves symlinks and rejects traversal, symlink escapes, symlinked parent directories, dangling symlinks, and writes in `read-only` mode.
- **Child environment allowlisting**: strict mode forwards only a minimal non-credential allowlist (`PATH`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TERM`, `COLORTERM`, `NO_COLOR`, `TZ`, `USER`, `LOGNAME`, `SHELL`, `DEVELOPER_DIR`) plus explicit `--env-allow` entries, isolates `HOME` and `TMPDIR` to the workspace, and strips provider API keys and ambient secrets.
- **Worktree-isolated subagents (`src/worktree.zig`)**: `--subagent-isolation worktree` (or `auto` for parallel batches in a git repo) runs each child in its own detached git worktree with a workspace-confined sandbox and read-only parent `.git` metadata so parallel edits cannot race on the parent working tree or modify repository hooks.

## Threat model

Treat model output, session imports, project files, tool results, extension code, plugin libraries, MCP executables, endpoint configuration, and downloaded web content as potentially hostile. The principal risks are unauthorized filesystem/process/network effects, credential disclosure through inherited environment or output, malicious code execution during explicit component loading, partial/unknown effects after interruption, and unsafe assumptions about isolation between child processes or native code.

The trusted computing base includes the Zpi binary and its dependencies, the user's OS account and filesystem permissions, selected provider endpoint/configuration, any executable path deliberately supplied by the user, and the terminal/parent process. The following are **not** security boundaries: `--cwd`, tool allowlists, `--no-tools`, a Node child process, MCP stdio, subagent conversation separation, cooperative cancellation, or a session file. They constrain workflow or protocol behavior but do not reduce OS privileges. In-process native plugins can corrupt or terminate the host process; child processes inherit the launching account's accessible resources and ambient environment unless the parent environment is externally restricted.

## Opt-in authorization and audit boundary

The secure policy is an in-process reference monitor, not an OS sandbox. `filesystem.write` gates the built-in write/edit tools, but this MVP has no standalone delete operation. Deletions and other filesystem effects performed inside shell commands, helpers, or already-started components are not separately intercepted; shell is authorized only at command dispatch. Capability IDs are exact: `filesystem.read`, `filesystem.write`, `process.exec`, `network.connect`, `clipboard.write`, `extension.load`, `native_plugin.load`, `mcp.start`, and `rpc.control`. The Harness tracks invocation, session, request, and persistent grants. Session grants expire on `/new` or a switch to another session. A request grant is consumed after its authorization record is written and synced. Persistent policy files require explicit selection in secure mode. The file must be regular, have a single link, be owned by the effective user, and have no group or other permission bits.

Each authorization event contains source, capability, target kind, mode, decision, outcome, policy source, reason, random per-run `runId`, and per-run `eventId`. An observed operation appends an event whose `parentId` is the authorization event. Pre-effect denials append only the authorization event. Tool selection happens before authorization, so a tool excluded by selection has no capability event. Targets are kind-only in this MVP; raw paths, commands, URLs, prompt text, arguments, credentials, file contents, and child output are not written to the audit sink. The sink is disabled by default, append-only when configured, exclusive-locked, and fails closed for secure/request authorization if it cannot append. Provider traffic, configuration/resource loading, session files, and effects internal to running extensions, plugins, MCP servers, and shell commands are outside this layer.

The host observes `allowed`, `failed`, `cancelled`, and `unknown` terminal states only where it controls the dispatch/completion boundary. Native library loading includes OS loader/constructor work before descriptor validation, so a load-time error is recorded as `unknown`; Zpi cannot claim that no code ran. A process, extension, MCP server, or native library may also perform effects beyond its startup boundary. Secure mode does not authenticate RPC peers, isolate native memory, scrub inherited environments, or roll back external effects.

## Fail-closed behavior and current tests

The [platform verification record](platform-verification.md#opt-in-capability-and-audit-regressions) lists the macOS arm64 current-tree matrix, TypeScript startup audit linkage, and the clipboard test with an injected runner. The clipboard test exercises the CLI adapter with a session grant for `process.exec` and a request grant for `clipboard.write`. It checks that missing process authorization does not consume the request grant, one copy succeeds, a second attempt is denied, and the audit links both authorizations without recording copied text. The helper is injected; physical OS clipboard behavior remains unverified.

- Tool allowlisting is applied to both declarations and dispatch. The disabled-write fake-provider test verifies that a model-proposed write does not create a file.
- MCP tool filtering/exclusions are checked against the server call log. This prevents the filtered call, but the explicitly requested MCP process remains trusted startup code.
- Extension gate denial is tested before the requested write effect; the fixture checks that the target file does not exist.
- Invalid credential/config/model routing/prompt input checks in `scripts/test-cli.py` assert failure before the named session path or explicitly missing plugin path has an effect.
- RPC validates frame size, UTF-8/JSON structure, depth/token bounds, supported command and prompt arguments. Errors are serialized on stdout; stderr is not a separate authenticated control channel.
- `web_fetch` blocks private/loopback/link-local and other reserved addresses by default, validates redirects and connected peers, and requires an explicit loopback opt-in for local fixtures.
- Session resume rejects unsafe file types/locks/corruption; an interrupted tool may have an unknown outcome and is not automatically replayed.

Run the available regression suite on the current host with Zig 0.17.0:

```sh
zig build test install
python3 scripts/test-install.py
python3 scripts/test-cli.py
python3 scripts/test-rpc.py zig-out/bin/zpi
python3 scripts/test-trusted-execution.py zig-out/bin/zpi
python3 scripts/test-ts-host.py "$ZPI_PI_SDK"  # when the supported SDK is installed
```

`scripts/test-trusted-execution.py` verifies target-scoped path/command/network rules, TUI one-time approvals and denials in a real PTY, structured headless denials, OS sandbox + environment isolation escape regressions across out-of-workspace writes, network access, child/grandchild processes, symlinks, MCP stdio servers, and the TypeScript extension host, worktree-isolated parallel subagents, and `--unattended` fail-stop execution. Linux Landlock+seccomp and `bwrap` execution must still be validated on a Linux host/CI runner; cross-compilation for `x86_64-linux-musl` and `aarch64-linux-gnu` is checked locally. Native C/Zig libraries remain in-process trusted code without memory or crash isolation.

## Policy decisions intentionally deferred

No new default permissions or approval UX are introduced here. Before adding project trust prompts, per-command approvals, remote RPC authentication, environment scrubbing, or process sandboxing, define the threat actor, compatibility impact, headless behavior, persisted policy, bypass semantics, and rejection behavior. In particular, tool selection must not be presented as consent to run explicitly loaded code, and process cleanup must not be presented as containment.
