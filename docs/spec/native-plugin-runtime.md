# Experimental native runtime contract

This document describes the experimental serial native runtime in `include/zpi_plugin_runtime.h` and `src/native_runtime.zig`. Independently compiled C and Zig shared-library fixtures pass on macOS arm64 and all four Linux guest combinations; the scope and limitations are recorded in [platform verification](platform-verification.md). The CLI accepts repeatable explicit `--native-plugin PATH` options and exposes their tools through `src/native_tools.zig`. The ABI remains provisional. The data types in `include/zpi_plugin.h` are the common value representation. Existing TypeScript support has its own Node host and version policy.

## Entry and negotiation

`zpi_plugin_descriptor_v1` returns a static, immutable plugin table before any instance is created. The host checks its fixed header, required prefix size, capabilities and all mandatory callbacks before calling `create`. This avoids creating an instance whose shutdown callback has not yet been validated. Host and plugin tables begin with ABI major, minor, structure size and reserved fields. Major versions must match; minor versions may add optional tail fields. Reserved fields must be zero. Required capabilities must be a subset of the host's advertised capabilities. The descriptor remains immutable through unload, and `create` must copy any host-table fields it retains. A host reads only fields covered by the plugin's declared size; the current host does not read the optional name tail. Loading requires an explicit absolute library path; no discovery or dependency installation occurs.

The initial runtime supports tool declarations and operations. Tool declarations contain name, description and a typed JSON Schema value. The agent adapter copies metadata while the library is loaded. Native tool names must be unique among registered tools, before CLI selection. TypeScript tools can replace a registered tool by name. Tools return a UTF-8 string or another JSON-compatible value; strings become result text directly, other values are serialized for the model, and the copied value is persisted as result `details`. Output text is limited to 50 KiB. Each operation may emit at most 1024 progress records and 1 MiB of aggregate progress text; progress conversion memory is released after its callback. Raw bytes require a separate encoding and are rejected by the JSON facade. Arguments must be objects; complete JSON Schema validation is not yet implemented. `--no-tools` loads explicitly selected plugins and disables their tools by default; `--tools` can explicitly enable them. `--no-builtin-tools` retains plugin tools. Allowlist/modifier selection and final exclusions apply to model declarations and dispatch together. TypeScript hooks wrap native tools when both systems are selected; TypeScript tool replacement follows its existing name precedence. Commands, providers and event hooks remain later capabilities. A library is trusted executable code; loading it can already run constructors before table validation.

## Single-thread operation lifecycle

All callbacks run on the host's calling thread, serially, without reentry. A plugin must not start background threads or retain host callback pointers in this initial capability set. `start` receives callback-borrowed arguments, working directory and call ID, and returns an opaque operation handle. Any inputs needed after `start` returns must be copied by the plugin before returning. The operation owns those copies until `destroy` returns.

`poll` must return promptly. It reports pending, progress, complete, failed or canceled. Pending carries no payload. Progress, complete and failed may transfer an owned value using the producer's release callback; canceled carries no payload. Pending and progress permit another `poll` before a terminal state. The host releases each output before polling again or destroying the operation. After a terminal state, only `destroy` is legal. Status codes distinguish callback contract errors from the operation's own failed result.

`cancel` is cooperative and idempotent. It does not release the operation or establish that work stopped. The host continues polling until a terminal state and calls `destroy` exactly once afterward. A nonterminal handle continues to pin the module, even after a deadline. If cancellation cannot drain it, the host reports an undrained operation and retains the module; it must not unload executing or retained code. A plugin whose callbacks block the calling thread cannot be interrupted safely by this in-process contract.

The agent adapter polls at 10 ms intervals and enforces a 30 second cooperative deadline between callbacks. It requests cancellation and polls for up to one further second during cleanup. Undrained handles and their modules remain pinned, and the affected tool becomes unavailable. Embedders can call `Entry.drainRetained` to retry cancellation/draining without replaying execution; the CLI currently retains them until process exit. Interactive `Ctrl-C` cancels cooperative polling between poll intervals and runs the same drain/cancel cleanup, while blocking native callbacks still cannot be interrupted safely. Progress is forwarded as `tool_execution_update` in JSON mode and text in the interactive terminal; print mode keeps final-response-only stdout. Wakeup callbacks and worker threads remain deferred.

## Ownership and shutdown

A successful `start` transfers one handle. A failed `start` must leave its output handle null and must have cleaned up partial work. Metadata remains plugin-borrowed until copied, and no metadata pointer is used after unload. Every transferred result graph stays immutable through its one matching producer release. A null release callback is allowed only for an entirely static, borrowed graph whose lifetime extends through operation destruction; the receiver still consumes the descriptor only once. No host allocator frees plugin memory.

The host tracks live handles and outstanding result descriptors. `close` fails while either count is nonzero. After all operations are terminal/destroyed and all results released, `shutdown` frees the plugin instance and returns success. Only then may the host close the dynamic library. A rejected shutdown leaves the module loaded. Creation failures must clean up partial state and leave the instance output null. The host validates the descriptor before creation. Callback and protocol errors after an operation starts leave that handle live; callers must cancel and drain it before destruction, or retain the module if draining is impossible. A successful poll transfers its output even if descriptor validation fails: the host invokes the producer's release callback on that error path. A failed poll callback transfers no output and must clean up any partial result itself. Module and operation wrappers must stay at stable addresses while their dependents exist; ownership wrappers must not be copied.

The C and Zig fixtures test producer release counts, input copies that survive the start callback, progress/terminal ordering, failed and malformed results, repeated cancellation, shutdown refusal with live work, and descriptor version/size/capability/callback checks. Rust support still requires a separately compiled Rust fixture before claiming execution evidence. Linux and macOS fixture execution is established for the current experiment, including CLI invocation, session result details, JSON progress events and the disabled-tools option. Ten separately compiled C libraries exercise missing/null descriptors, major/size/capability/callback rejection, failed creation, reserved fields, and compatible short/extended table layouts. Rust fixtures, retained leases, complete JSON Schema validation, concurrency and safe handling of blocked callbacks remain open; do not freeze this contract.
