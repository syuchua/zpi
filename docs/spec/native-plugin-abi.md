# Native plugin ABI design

Status: experimental native runtime with C/Zig typed values and JSON conversion. `include/zpi_plugin.h`, `include/zpi_plugin_runtime.h`, `src/native_plugin.zig`, `src/native_json.zig` and `src/native_runtime.zig` define provisional value layouts, bounded conversion, version/capability table checks, explicit dynamic loading, tool metadata and serialized poll/cancel/result ownership. Separately compiled C and Zig shared-library fixtures each pass seven runtime tests on macOS arm64 and all four Linux guest combinations; ten additional C malformed-library descriptors reject incompatible/missing/short tables and pass compatible old/new sizes on each platform. Their tools also pass fake-provider CLI invocation, progress, session reload and `--no-tools` integration on each guest; details are recorded in [platform verification](platform-verification.md). This is not a stable ABI: no native ABI is frozen and TypeScript compatibility remains distinct.

## Purpose and expected benefits

Zpi will load trusted native dynamic libraries through a language-neutral C ABI. Zig implementations use `extern struct` and `callconv(.c)`; C uses a published header; Rust uses `#[repr(C)]` and `extern "C"`. Modules are built separately for a specified OS, CPU architecture and C ABI. They do not depend on Zig's internal type layout or the host compiler version.

Native loading can avoid provisioning a JavaScript runtime and SDK dependency graph, reduce startup/idle memory, and make frequent callbacks inexpensive. The benefit depends on the plugin: network/model latency and child-process tools may dominate total time, and native libraries can still allocate heavily. pi-rust's primary ABI sends structured values as JSON strings, so a native function call does not imply zero-copy or zero-serialization. Its whole-program pi comparison does not measure the ABI's isolated effect. No numeric advantage is asserted before Zpi measurements exist.

## Separate invocation, representation and transport

RPC is a request/response and lifecycle model, not a data encoding. JSON-RPC still parses/encodes JSON. Binary RPC can reduce encoding cost, but adds framing, bounds validation and schema/version handling. Shared memory is a transport/storage mechanism; it does not itself define message semantics, eliminate decoding, or guarantee zero-copy.

Use one semantic contract with separate adapters:

| Layer | In-process native plugin | Optional child-process extension | JSON/TypeScript compatibility |
| --- | --- | --- | --- |
| Invocation | C function tables and opaque operation handles | Framed request IDs, progress, cancellation, terminal result | Same logical operations via explicit host adapter |
| Structured data | Read-only C-compatible typed value views and fixed event records | Versioned framed binary wire format selected after fixture/benchmark evaluation | Public JSON-compatible API translated at the boundary; avoid stringify → parse round trips internally |
| Large data | Immutable pointer/length buffers with owner-managed lifetime | Inline bytes first; optional negotiated shared-memory blobs later | Explicit blob descriptor or compatible JSON encoding, depending on negotiated interface |
| Lifetime | Callback borrow or explicit retained immutable lease | Message-owned decoded data or leased mapped blob | Adapter owns conversion buffers and releases them by the same contract |

Do not send C ABI pointer-bearing structs as a wire format. Do not route every native plugin call through an IPC protocol. JSON compatibility means preserving the documented JSON data model and API behavior, not automatically reproducing pi extension SDK semantics.

## Proposed native v1 boundary

- The experimental entry symbol `zpi_plugin_descriptor_v1` returns the fixed header of an immutable static function table. Validate major/minor, structure size, reserved fields, required capabilities and mandatory callbacks before `create` receives a callback-borrowed host table. Major mismatches fail; optional appended callbacks are read only after size/capability checks. This descriptor-first design establishes cleanup callbacks before allocating a plugin instance. See [runtime contract](native-plugin-runtime.md); the symbol and table remain provisional.
- Use fixed-width status/tag fields, explicit pointer/length byte spans and opaque handles. Specify C `size_t`/Zig `usize` only for target-local lengths; never assume the same layout across architectures. Null pointers are valid only with zero length or where explicitly optional. No Zig slices, allocators, error unions, Rust `String`/`Vec`/`Result`, language exceptions or GC objects cross the ABI.
- Fixed records carry frequent event metadata (event kind, operation ID, flags, content kind) and references to payloads. Experimental `zpi_value` records represent null, boolean, signed/unsigned integer, finite float, exact-number text, UTF-8 string, bytes, ordered list and ordered object entries. Zig validates descriptors, lexemes, UTF-8, duplicate keys, nesting and aggregate bounds; JSON conversion is in `src/native_json.zig`. `zig build test` covers C/Zig layout and exact-u64 round-trip/release, nested JSON and a C dynamic library lifecycle fixture.
- Preserve numeric meaning: large JSON integers and decimal lexemes can use exact-number text instead of silently rounding through f64. Define rejection/normalization of duplicate object keys, invalid UTF-8 and non-finite numbers at each adapter. JSON-compatible values have one canonical logical meaning; raw bytes use an explicit compatibility encoding and are not implicitly treated as JSON strings. Exact source-text fidelity is a separate optional raw-JSON feature.
- Views are immutable for their documented lifetime. A callback-local borrowed input cannot be retained or accessed from a worker after the callback returns. Asynchronous operations must copy inputs into their own arena, or acquire an explicitly supported immutable lease that pins the complete backing graph. No unretained nested pointer may outlive its owner.
- Owned outputs carry a matching producer-side release callback and context. The receiver releases exactly once using that producer's function, never its own allocator. Large read-only buffers may use the same lease mechanism. SDK wrappers implement language-native RAII/defer cleanup; the ABI carries only C-compatible descriptors and functions.
- The ordinary Zig runtime and native ABI exchange typed values/events and never stringify then parse them merely to cross an in-process call boundary. Implement JSON conversion in a facade at public JSON/RPC/JSONL inputs and outputs: parse the JSON input once into the core value representation and serialize once when producing JSON. JSON-backed configuration, session logs and JSON Schema tool declarations remain JSON formats; compile/validate their schema once when practical instead of re-encoding/re-parsing it per tool call.
- A compatibility facade should preserve JSON null/boolean/string/array/object behavior and JSON object ordering where contractually observable. Represent signed/unsigned integers explicitly; retain the exact decimal lexeme or explicitly reject numbers beyond the interoperable numeric range when the conversion policy requires it. Never silently route exact integers through `f64`. Document duplicate-key, non-finite, invalid UTF-8 and byte-value behavior. “JSON-compatible” promises semantic interoperability, not preserving whitespace or exact source spelling of the original JSON document.
- If an extension requires the historical JSON-string ABI, negotiate a separate fallback capability/tag and convert at that boundary; do not make JSON stringify+parse the default for Zig/C/Rust plugins. Structure traversal, allocations and copies can still occur with typed views. Claim zero-copy only for a named path whose immutable buffer owner/lifetime has been proven.
- Bound depth, node count, aggregate string/byte sizes and per-result data. The typed representation can still incur traversal, allocation and copies; "zero-copy" may be claimed only for a particular buffer path with proven ownership and benchmark evidence. C pointers remain trusted-plugin memory; size validation cannot make arbitrary plugin pointers safe.
- Registration initially covers tools, commands and event hooks. Providers follow through negotiated optional table tails. Direct host state pointers and TUI objects are outside the first ABI; add explicit operations as those surfaces mature.
- Tool execution returns a handle. A non-blocking progress/poll interface returns pending, completed or failed status; cancellation is cooperative and idempotent and does not free a handle. Specify which thread may poll/destroy, which callbacks may be concurrent/reentrant and how notifications wake the host before freezing v1. Cancellation alone does not prove the operation stopped or permit freeing inputs.
- Host and plugin callbacks report errors using status plus bounded error data. C++ exceptions and Rust unwinding must be contained on the producing side. Zig panics, process aborts, segmentation faults and arbitrary memory corruption cannot be reliably contained by this in-process ABI.
- All callbacks, plugin release functions, threads, handles and buffers pin module lifetime. Shutdown requests cancellation, drains operations, releases data and stops threads before unload. If work cannot be drained, retain the module and report the condition; forcibly unloading executing code is invalid. Hot reload is not promised in v1.

## Cross-process data plane

Use an explicit transport interface so a future Node compatibility host or isolated native worker does not change the agent/tool semantic model. Start with bounded framed messages over pipes or a local socket, operation IDs and length validation. Before implementing binary IPC, evaluate MessagePack/CBOR versus a schema-oriented format such as FlatBuffers/Cap'n Proto using representative payloads and implementation/dependency cost. Selection requires evidence; no wire library is chosen merely for a zero-copy marketing claim.

Do not implement shared-memory rings for ordinary tool arguments in the MVP. If large image/file/tool-output measurements justify a fast path, use a small control message plus an immutable blob in shared memory. Specify mapping creation/handle transfer on macOS and Linux, region ID/generation, offset/length, overflow-safe bounds checks, completion acknowledgments, reference ownership and crash/disconnect reclamation. No process-local pointer crosses a process boundary. Reusing a region requires proof that every reader has released it. Streaming queues also need bounded capacity and backpressure; shared memory without those contracts can increase peak memory or deadlock.

A separate worker can contain process termination. Shared memory and IPC do not themselves sandbox that worker's filesystem/process/network permissions.

## Trust and compatibility

Native plugins execute with the host process's privileges. A C ABI is an interoperability boundary, not a sandbox or memory-safety boundary. Loading project-local executable code follows an explicit trust decision. A future subprocess mode can separate process failures; OS restrictions require a separate sandbox design.

The first SDK targets Zig and C, with Rust supported by the same C contract. Claim tested Rust interoperability only after a Rust-produced fixture passes. Compatibility with pi-rust's exact `rpi_plugin_register` contract is not implied: it has its own API tables, semantics and version policy. Existing pi TypeScript extensions remain a separate compatibility target requiring a JS runtime and SDK adapters; native ABI delivery does not satisfy that requirement.

## Delivery and acceptance

1. Publish provisional C declarations, matching Zig types and an experimental serial lifecycle contract. Value validation, JSON conversion, C/Zig layout, descriptor size/capability checks, malformed terminal cleanup and ten independent malformed-library fixtures are implemented. Other ABI evolution and security cases remain open; keep the interface experimental.
2. The explicit-path loader and independently compiled C and Zig tool/poll samples run on macOS arm64 and all four Linux guest combinations. Fake-provider CLI fixtures exercise both modules without credentials. A Rust-produced fixture remains required before advertising Rust interoperability.
3. Native tests exercise metadata lookup, typed values, progress/completion/cancellation, close refusal while busy, operation destruction, producer release counts, adapter result persistence and cooperative deadline cleanup. CLI registration and JSON progress delivery are integrated. Exported retained leases, callback-error matrices and proving non-cooperative blocked callbacks remain incomplete.
4. Executable rejection fixtures cover missing symbol, null descriptor, wrong major, short header, unsupported capability, missing required function, failed create and nonzero reserved field; compatible exact-prefix and extended-minor tables are accepted. Old/new plugin lifetime behavior is fixture-tested within this initial single-thread contract; table evolution policy remains provisional.
5. Test nested/list/object values, exact large numbers, UTF-8, binary data, malformed JSON adapter input and bounds. Verify semantic equality across typed and JSON paths; do not confuse this with byte-for-byte JSON text fidelity.
6. Run fixtures on macOS and Linux. Cross-compilation is additional evidence, not a replacement for execution.
7. Freeze ABI v1 after these tests pass; preserve compatible struct prefixes and reserve breaking changes for a major version. Binary IPC and shared-memory delivery remain separate optional gates; native ABI completion does not require them.

## Benchmark contract

Compare host only, host plus an idle native plugin, and an equivalent optional TypeScript compatibility host. Measure cold start/load time, process-tree steady/peak memory, no-op invocation p50/p95, throughput, serialization/allocation counts, payload sizes and repeated load/shutdown behavior. Within the native host compare JSON-string callbacks against typed views using identical logical data, including tiny arguments, nested objects, text deltas and large byte buffers. For future IPC compare inline binary messages to shared blobs including mapping/control/synchronization overhead, concurrent load, backpressure and worker crash cleanup.

Report build mode, compiler/runtime versions, OS/CPU, raw samples and method. Separate ABI microbenchmarks from model/network latency and end-to-end workflows. Establish a break-even payload/workload before adding shared memory; no hard threshold or numeric speedup is claimed without reproducible baselines.
