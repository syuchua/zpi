# Zpi Implementation Specification

Status: evolving design contract for the active project goal. Architecture decisions are refined using executable evidence. Current support and deferred work are summarized in [README.md](../../README.md) and the [compatibility matrix](compatibility-matrix.md). This is a product and architecture contract, not a claim of feature parity. The original project is an empty directory; Zig 0.17.0 is installed locally. The macOS arm64 host and local Apple Container/Colima Linux guests are available for execution tests; see [platform-verification.md](platform-verification.md).

## Sources and scope of comparison

Reference checkouts are pinned in local git metadata at `earendil-works/pi` commit `c815ddaa3736bd0b009ce6a997ee5003f8a3a532` and `bigfish1913/pi-rust` commit `668d7d7b570954715f7781bf22e005ad83d51b2e`. They are comparison material only and are not dependencies or shipped code. Review surfaces include upstream agent-loop and provider types; coding-agent CLI, extension, session, provider, and JSONL documentation; example extensions; and pi-rust architecture, harness, and plugin SDK documentation. The pi main branch and feature set change: compatibility claims must name a source revision.

Pi is a TypeScript/Node agent toolkit and CLI. Its product includes the multi-provider `pi-ai` message/stream API, streaming agent loop, branchable JSONL sessions and compaction, terminal UI, CLI/print/JSON/RPC/SDK interfaces, TypeScript extensions, skills, prompt templates, themes, packages, custom providers, and MCP. Its session entry format is tree-based JSONL with versioned headers, message/provider/model metadata, tool results, compactions, custom entries/messages, settings changes, labels, and branch operations. Extensions run in-process via Node and jiti, import pi SDK packages and Node modules, and register tools, providers, commands, event hooks, UI renderers, and other resources.

pi-rust demonstrates a useful native decomposition: AI/providers, runtime/configuration, agent loop, tools/execution environment, persistent harness, TUI, stable plugin ABI/loader, and CLI. Its Rust `cdylib` ABI and Rust plugin ecosystem are distinct from pi's TypeScript SDK; this does not establish interoperability with pi extensions.

## Product objective and boundaries

Build a distributable, usable Zig terminal coding agent, progressing from an executable specification through a tested MVP and an explicitly measured compatibility program to production readiness on macOS and Linux. Prefer pi user-visible behavior and portable session formats when practical. Keep boundaries modular so the runtime can later be embedded. Windows, exact parity with every moving upstream release, and importing Rust plugins are not initial acceptance criteria. Do not copy reference implementation code; preserve upstream license notices if any material is later reused.

### TypeScript extension feasibility and decision gate

Existing pi extensions are executable JavaScript/TypeScript programs targeting Node APIs and pi-specific imports (`@earendil-works/pi-coding-agent`, `pi-ai`, `pi-tui`, TypeBox, and transitive packages). Zig cannot execute TypeScript directly. Running `.ts` would require bundling/providing a Node or Bun runtime (or an embedded compatible JS engine with module, Node API, npm-package and SDK shims); merely implementing a plugin ABI or invoking `node` is not equivalent. Pi-rust's native C ABI is a model for a **new** extension ABI, not a bridge for pi extensions.

Feasibility research found that the locally installed pi 1.5.2 Node package exports its real extension loader and runner, including jiti module aliases for SDK and TypeBox imports. An independent probe loaded and invoked real extension code with that loader; this establishes feasibility for a bounded input/tool-hook subset, not compatibility of Zpi today. The installed package may differ from the pinned post-release source even at the same version. First implement an explicitly configured host using a user-provided Node/SDK installation: no automatic project discovery or dependency installation. Send bounded, correlated IPC requests; define cancellation, failure and ownership behavior, run unmodified upstream examples in fixtures, and expose unsupported context/actions as errors rather than plausible fake state. Pi documents throwing `tool_call` handlers as blocking execution; preserve that fail-closed behavior. Project-local code requires explicit trust; an explicit extension path is user-selected, while future auto-discovery must have a separate project trust gate. Node and the extensions retain the user's OS privileges. Assess package licensing and exact version provenance before distribution.

The user explicitly added a native plugin ABI as a product target. Design a documented, versioned, language-neutral **C ABI**, implemented by Zig using `extern struct` and C calling conventions, for tools, commands, events and later providers. This target is additive to the requested existing-pi TypeScript compatibility investigation. Keep the native core usable without a JavaScript runtime; an explicitly configured compatibility host may provide Node and SDK shims for a stated subset of existing pi `.ts` extensions. Neither native plugins nor a JavaScript compatibility host implies sandboxing, and project-local code requires explicit trust. Before implementing a TypeScript compatibility host, assess maintained Node distribution, SDK shims, dependency/module resolution, asynchronous callback lifecycle, cancellation, and security. If meaningful compatibility is infeasible, document the measured gap and ask the user to approve the replacement boundary before closing the parity task; do not silently treat native plugins as TS compatibility.

## Layering and key contracts

Keep acyclic module direction and public types independent of terminal rendering and storage:

1. `core`: allocator/error conventions; provider-neutral content, messages, tools, usage, model metadata, and typed agent events.
2. `provider`: `Provider` interface for model listing and cancellable streaming completion; protocol implementations translate to/from core types. First live implementation is OpenAI-compatible Chat Completions with SSE and environment/config credentials. Anthropic Messages is the next independent adapter. Preserve tool-call IDs and fragments, finish/error/usage, reasoning, multimodal types and unknown metadata where the provider supports them; report unsupported content explicitly, never silently corrupt it.
3. `agent`: deterministic event-driven run loop; stream assistant updates, execute declared tool calls, append results, continue until a non-tool final response, cancellation or configured step/deadline limit. Tools receive an execution context, cancellation and policy gate. All effects pass through a replaceable `ExecutionEnv`; tests use deterministic fake provider and memory/fixture environment.
4. `session`: append-only JSONL, versioned header, stable entry IDs and parent IDs; active leaf selects branch context. Proposed recovery accepts a valid committed prefix after a truncated last line and reports corruption with line number. This stricter diagnostic behavior is an intentional difference from the pinned pi parser, which skips malformed records. Session effects and external tool effects are not exactly-once. Preserve unknown entry types/fields for round-trip where possible. The offline pi v3 importer projects the last entry’s ancestry into a new linear Zpi session. It validates the tree links and supported active messages before publishing the destination, and it never dispatches imported tool calls. The converted transcript carries text, the original working directory, and complete tool batches. Provider selection and tool declarations come from the invocation that resumes the transcript. Export and round-trip preservation of the pi tree remain portability goals.
5. `tools`: bounded `read`, `write`, `edit`, `grep`, `find`, `ls`, and `bash`; validate arguments; resolve relative paths from the configured project cwd; enforce documented output/time limits. Match pi's process-permission model by default: project trust governs resource loading, and enabled tools operate with the launching user's permissions. A tool hook may provide an explicitly configured approval policy. Neither the working directory nor such hooks are an OS sandbox. Do not introduce mandatory per-tool approval as an unrequested compatibility change.
6. `harness`: compose resources, config, provider, tools, agent, persistence and events without requiring TUI; own per-run lifecycle and cleanup.
7. `tui`: terminal capabilities, input/editor, transcript, streaming redraw, dialogs and selectors; degrade to text on non-TTY, handle resize and cancellation. No model protocol, credential, or session-tree logic belongs here.
8. `plugin`: a versioned, language-neutral native C ABI is a required product target. Specify it with a C header and Zig SDK, then verify a dynamic loader against independently compiled fixtures before declaring it stable. Include version/structure-size negotiation, explicit buffer ownership and producer-side release functions, opaque operation handles, cooperative cancellation, lifecycle cleanup and documented thread rules. Use typed C-compatible immutable value views and event records for native calls; keep JSON conversion at external/legacy compatibility boundaries. Asynchronous consumers copy callback-borrowed data or acquire an explicit immutable lease. Future subprocess transport uses separate bounded wire messages; shared-memory blobs require measured benefit and an offset/lease/reclamation protocol. See [native-plugin-abi.md](native-plugin-abi.md) for the data exchange design. Language exceptions/unwinding must not cross the boundary; a Zig panic, abort, invalid pointer or memory corruption in an in-process plugin can terminate/corrupt the host. ABI validation does not provide crash containment. Treat native plugins as trusted code. A subprocess transport may later provide process separation where needed.
9. `cli`: `zpi` entry point; `--help`, `--version`, interactive regular TUI, `--print`, structured JSONL event mode, explicit provider/model selection and explicit models-file override, session continuation by path, `--no-session`, working-directory selection, proxy override, and tool disablement. stdout is reserved for final response/protocol data in print/JSON modes; diagnostics go to stderr. MVP config reads a deliberately small OpenAI-compatible subset with bounded provider/model custom headers; command-valued credentials, OAuth and other provider APIs are explicit unsupported cases, not silent fallbacks.

Core acceptance requires Zig 0.17.0 (pin `minimum_zig_version` and CI accordingly); use stdlib APIs available on that pinned release, with platform-specific boundaries isolated and cross-compilation checks. Pin direct external dependencies and document ownership/licensing. macOS and Linux are release targets (x86_64 and arm64 where CI runners/tooling permit). Runtime requires network access only for remote providers, credentials supplied via environment or private user configuration, and a POSIX shell for the MVP bash tool. No API key is needed for unit tests.

## Staged acceptance

### Spec gate

Maintain this specification plus a capability matrix: pi reference behavior, Zig design/status, automated/manual evidence, deviations and revisit condition. Confirm Zig version and cross-target CI availability, JSON/HTTP/SSE and terminal dependency choices, provider order, session schema subset, plugin transport, config paths, trust/approval defaults and threat model. Resolve the TypeScript extension feasibility gate above before representing extensions as compatible. Validate licenses and vendor/dependency choices. No feature is considered implemented from documentation or a type definition alone.

### MVP gate

A fresh checkout builds with pinned Zig using documented commands. No-key offline tests exercise argument parsing, provider-neutral message/tool-call parsing, deterministic agent tool round-trip, error/cancel/step-limit paths, session JSONL save/reload/branch/corruption handling, bounded file tools, and shell timeout/process-group cleanup. A checked-in local HTTP fake-provider integration exercises CLI print and JSON event modes against a full tool loop plus persisted-session resume. An actual interactive user can configure an OpenAI-compatible provider and model through environment/config, submit prompts, observe streamed text, run `read`/`write`/`edit`/`bash` tools under the documented policy, and resume a persisted session. `--print` and JSONL event output work non-interactively. At least one local fake HTTP/SSE integration test validates request headers/body, stream chunking/tool-call assembly, error reporting and clean stdout. Documentation covers install/build, configuration, credentials, approvals and known limitations. This is a usable vertical slice, not broad parity. Cross-platform evidence is produced with both the Apple `container` runtime and Colima: build arm64 and emulated amd64 Linux artifacts on macOS and execute all no-key Zig unit/fake-HTTP suites in both Linux runtimes. The Python localhost CLI integration and live model-provider check are run on native macOS only. Preserve layer-specific outputs and logs as CI artifacts. Native macOS execution remains required; a Linux container does not establish Linux ABI/plugin behavior until native plugin fixtures execute there.

### Compatibility/parity gate

Use a maintained matrix rather than the phrase "full compatibility" alone. Prioritize provider-neutral conversation and tool semantics, CLI modes/events, shared JSONL entries, session resume/branching/compaction, model configuration and credential resolution, core tools and approval semantics, resource loading, TUI workflows, then extension surfaces. Implementing several providers is not evidence that all pi provider auth/API variants work. Track each reference behavior as compatible, intentionally different, unimplemented or blocked, with version and reproducible evidence. Exercise golden JSONL fixtures from the pinned pi revision and deterministic extension/provider fixtures. TypeScript compatibility may be accepted only for an explicitly enumerated subset proved by executable fixtures; otherwise obtain user approval for the alternative before final parity acceptance. Include pi-rust's library/runtime separation, cancellation/recovery, offline-testable environment and extensibility where they improve the Zig product, without claiming pi API equivalence.

### Native plugin ABI gate

Ship a C header, a Zig SDK, version negotiation and loader, and at least a Zig plugin plus an independently compiled C fixture. Rust is a supported design target via `#[repr(C)]` and `extern "C"`, with a Rust fixture required before claiming tested Rust interoperability. Exercise registration, execution/progress, cancellation, error return and cleanup; reject incompatible major versions, truncated mandatory function tables, missing symbols and absent required capabilities before dispatch. Test old/new optional table tails, buffer release counts and in-flight operation lifetime. Verify typed-value/JSON-adapter semantic equivalence, exact-number handling, nested-data bounds and asynchronous copy/lease lifetimes. No compiler-specific Zig/Rust slices, error unions, allocators, containers or language-owned values cross the ABI. Never unload a module while its callbacks, threads, handles or buffers remain live. ABI stability applies to a specified OS/architecture and C ABI; it is not one portable plugin binary for every target. These fixtures and rules are required for the parity task even if early MVP delivery precedes plugin loading.

Measure the native plugin's benefit with reproducible benchmarks: host only, host plus an idle native plugin, repeated no-op and realistic plugin invocations, repeated load/shutdown, and a comparable optional TypeScript host. Record cold-start/load time, latency distribution, throughput, peak/steady process-tree memory, CPU, buffer allocations/copies and payload sizes, with compiler/build/OS/architecture and raw samples. Keep provider network/LLM time out of ABI microbenchmarks and also report a representative end-to-end tool workload separately. No numeric speedup or memory-reduction target is claimed until baselines exist. pi-rust's whole-program comparisons to pi do not isolate the ABI's contribution, and its JSON-bearing C ABI still incurs serialization/allocation work.

### Production gate

Run clean macOS and Linux builds/tests across the supported release targets; record which were native, cross-built, translated or guest-executed. Keep format, offline CLI, provider, session, plugin, security-boundary and PTY evidence reproducible. Produce reproducible, checksummed release artifacts. Provide an installation, upgrade, rollback and uninstall guide and a version and session-format compatibility policy. The [source installation guide](../install.md) covers the current development builds. Document supported providers and auth modes, configuration precedence, trust boundaries, executable effects, plugin risks and threat model. Continue testing malformed/oversized network input, SSE framing, timeout/cancellation paths, session recovery, path/symlink boundaries, shell output/time bounds, secret redaction, stream backpressure and terminal resize/redirect behavior. Run release smoke with isolated home/config and no ambient credentials. Publish remaining matrix gaps and benchmark methodology. Do not claim OS sandboxing, exactly-once recovery, full pi parity, or production readiness while acceptance gaps remain.

## Verification and execution policy

Each phase is complete only with checked-in artifacts and repeatable evidence. At minimum run `zig build test`, `zig build`, executable help/version/print smoke tests, formatting (`zig fmt --check` over tracked Zig sources), fixture-based protocol/session tests, and macOS/Linux CI. Use a local fake server and isolated temporary home for model-flow smoke tests. Record exact Zig version, OS/architecture, command, outcome and any skipped check. Never put secrets in fixtures or logs. Network-dependent provider checks are supplementary and must state when not run.

If a concrete blocker is encountered, isolate and investigate it, record attempted commands/evidence and alternatives, and ask the user for a decision where scope or compatibility needs changing. Do not silently waive a gate, weaken an approval/security boundary, or mark the long-term goal complete while its stage tasks remain open.

## Decision record

- Product scope is a terminal coding agent; macOS and Linux are targets, Windows is deferred.
- Existing pi TypeScript extension support was implemented as an explicitly selected compatibility host using the real user-installed pi SDK. See the extension host document for the tested subset and limitations. Do not conflate this with the native ABI.
- Native plugin support is a distinct experimental target using a language-neutral C ABI; C and Zig fixtures have execution evidence. Rust interoperability, stability and performance benefits are not established until fixtures and benchmarks exist.
- Native calls use typed values; JSON remains at JSON-facing boundaries. Separate future IPC framing from native memory layouts. Shared memory is conditional on workload measurements.
- Default tool execution follows pi's process-permission model; project-resource trust and optional approval hooks are separate mechanisms. Neither project cwd nor plugin ABI is a sandbox.
- Provider support is an OpenAI-compatible Chat Completions adapter plus an Anthropic Messages text/tool subset, not general multi-provider or auth parity. Provider work remains evidence-based and version-scoped.
- Current evidence is host-native macOS arm64 plus Linux arm64 native and arm64/amd64 musl guest execution, with translated amd64; see [platform-verification.md](platform-verification.md). Native x86_64 release and performance verification, Intel macOS, Linux SDK execution and signed release artifacts remain open.
