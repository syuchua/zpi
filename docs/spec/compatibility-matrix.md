# Pi Compatibility Matrix

Reference revisions: pi `c815ddaa3736bd0b009ce6a997ee5003f8a3a532`; pi-rust `668d7d7b570954715f7781bf22e005ad83d51b2e`. The reference column records inspected upstream contracts; the status column records current Zpi evidence. MVP implementations cover a subset and do not establish full pi compatibility. Status changes require checked-in fixtures/tests or a reproducible manual run. Compatibility is declared per API family and behavior, not by provider vendor name.

Status: `not implemented` = absent in this checkout; `research needed` = exact scope/priorities must be decided against pinned sources; `candidate deviation` = deliberate candidate where parity is unsafe, impossible, or costly, requiring explicit compatibility documentation. None is silently considered compatible.

The implementation is a tested, useful subset, not daily-use parity with pi and not yet a production-ready release. There is no fullscreen editor, steering/retry or compaction, no sandbox or general project trust UI, and provider/auth coverage is narrow. TypeScript extensions require Node and a supported pi SDK (`1.5.2` or `1.6.0`). The native C/Zig ABI is experimental, Rust interoperability is untested, and releases are local checksummed archives; CI provenance/signing is not yet established. Linux has one successful Ubuntu arm64/glibc SDK-host verification; other Linux runtime combinations still lack SDK execution evidence. See [the platform record](platform-verification.md) for evidence boundaries and outstanding production acceptance.

## Decision questions that remain open

1. Select exact supported Zig release floor after verifying the intended CI/release channels. Zig's rapid version changes make a minimum version and release artifacts necessary.
2. Confirm primary CI architecture matrix and actual Linux execution evidence before promising release support.
3. Select transport, HTTP/TLS/SSE and TUI dependencies against macOS/Linux packaging and licensing; first-provider family and model catalog source need tests.
4. Define the first pi JSONL compatibility subset precisely. Never emit a pi-versioned file that silently changes model context by dropping unsupported context-bearing entries.
5. Prioritize feature families rather than claiming parity based on the number of vendor names: chat API, model features and authentication flow are distinct dimensions.
6. Decide in-process versus external Node runtime for any TypeScript extension host. Small API-stub experiments prove JavaScript callback logic only, not SDK/module compatibility.
7. Freeze native ABI entry/table and wakeup/thread contract only after Zig, C and Rust fixtures pass independently. Isolated performance/memory benchmarks establish measured benefits rather than assumed gains.
8. Choose project trust and per-tool approval defaults. Pi does not intrinsically prompt before every tool; stronger defaults are intentional compatibility/safety tradeoffs.
